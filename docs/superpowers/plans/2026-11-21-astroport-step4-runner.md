# AstroPort step 4: the build job runner (astroport-run) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Rust binary `astroport-run` that turns the user's own Astro Bot dump into the run folder `<data>/generated/run-<version>/` as an AGS extension job, reporting progress as JSON lines, plus a `status` query so the adapter can tell "missing", "stale" or "ready".

**Architecture:** One standalone crate `runner/` (lib + bin). `build` runs five steps: check the dump and its version, unwrap `eboot.bin` and every `sce_module/*.prx` (a Rust port of AnyPS5's `tools/unwrap_self.py`), one call of the AnyPS5 relinker (it relinks the game and every module in `<input dir>/sce_module/` itself, writing `AstroBot`, `app0/sce_module/<module>.guest.prx` and the `.registry.json` / `.needed.json` files beside its output), lay out the run folder, write the result record. Everything is produced in `<run>/.stage/` and moved into place by rename, and files from the install folder are copied then renamed, so a mapped copy is never written in place.

**Tech Stack:** Rust (edition 2021, as `patcher/Cargo.toml`), `serde` + `serde_json` + `sha2`, `std` for everything else (no CLI or temp-dir crates).

**Spec:** `~/Games/astrobot-pc/native/docs/superpowers/specs/2026-11-21-astroport-design.md` (sections 5.2, 5.3, 9 step 4). Job protocol: `~/projects/AGS/.claude/worktrees/extension-protocol-2/docs/superpowers/specs/2026-11-21-extension-protocol-2-design.md` section 7.1 and 9.3. Job protocol names, fields and rules come only from the AGS milestones 2-5 interface sheet, `~/projects/AGS/.claude/worktrees/m2-m5-plans/docs/superpowers/plans/2026-11-21-m2-m5-interfaces.md` (the "sheet"; its sections written `sheet §n`): §3.2 `job.plan`, §3.3 worker and progress FD, §3.4 cancel and cleanup, §3.5 generated executables, §3.9 admission. Every job-protocol detail is behind `runner/src/progress.rs`; what the sheet leaves open is marked `SHEET:`.

## Global Constraints

- Never start the game, AnyPS5, AGS or any service in any step. Tests use fixtures generated by the test itself. The opt-in integration test (Task 6) only READS the owner's dump and `~/Games/astrobot-pc/native/src-1019` and writes only into a temp folder.
- Every test command has a hard timeout (`timeout <seconds> ...`). Tests that spawn a child (python3, the fake relinker) also give the child a `timeout`.
- Never modify a game dump: the runner opens dump files read-only and never writes through a link into it (the relinker writes through links, so `app0/sce_module/` is always a real folder).
- Never add game files, firmware `.prx`, keys or `ngx-sdk` to the repo. No fixture is committed as a binary: SELF/ELF/`.prx` fixtures are built in memory by the tests.
- No tracked file contains the owner's home path (`scripts/check-repo.sh` rejects it): write `~/` in docs, read real paths from env vars in tests.
- `runner/` is a standalone crate: its own `Cargo.toml` and `Cargo.lock`, no root workspace; `edition = "2021"`, `license = "GPL-2.0-only"`, dependency style `name = "1"` as in `patcher/Cargo.toml`.
- The user's machine needs no Python: the runner never calls python3. Only the parity tests call `python3 -I engines/anyps5/tools/unwrap_self.py`.
- The binary keeps the name `AstroBot` (the patcher matches it).
- Supported versions 1.018 and 1.019, title `PPSA21567`. Unsupported message, verbatim from the design: `Version 1.0xx is not supported. AstroPort runs 1.018 and 1.019.`
- Fonts are never shipped: missing Noto fonts stop the job with `Install the Noto fonts`.
- No push and no release without the owner's OK. Implementers cannot commit; the controller runs each commit step exactly as written. Every commit message ends with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Only these files are created or edited: `runner/**` and this plan. Anything needed in `.gitignore`, `scripts/check-repo.sh`, `README.md`, `NOTICE.md` is listed in "Prelude and wrap-up needs".
- No `launch` subcommand: design 5.3 makes `argv[0]` the relinked `AstroBot` itself and the launch env comes from the adapter's `launch.plan` (step 3), so the runner has nothing to do at launch.

## Review Focus

1. The run folder from an older hand-built setup has `app0/sce_module` as a symlink into the dump: the build must replace the link (never its target) with a real folder, and the dump stays byte-identical. Test: Task 4 `sce_module_link_is_replaced_not_followed`.
2. A dump whose `eboot.bin` or modules are already plain ELF (decrypted "fixed" dumps): they are copied unchanged, not refused as "not a SELF container". Test: Task 2 `plain_elf_is_copied`.
3. A run folder that already holds real save folders (`_sd`, `_sd_mem`, `_trophy` with files, from a copied hand-built run folder): never deleted; the job stops with a message naming the folder. Test: Task 4 `real_save_folder_with_files_stops`.
4. A build killed mid-way (cancel = SIGTERM to the group): `status` reports `stale` or `missing`, never `ready`, and the next build removes `.stage/` and succeeds. Test: Task 5 `interrupted_build_is_not_ready_and_rebuilds`.
5. Dump paths with spaces and brackets (the owner's own dumps are named like `[XX] Astro Bot 01.018 PPSA21567 FIXED`): links, relinker arguments and the record keep the exact path. Test: Task 5 fixtures use a dump folder named `[DL] Astro Bot 01.019 PPSA21567`.

### Task 1: Crate, error type and progress lines

**Files:**
- Create: `runner/Cargo.toml`, `runner/Cargo.lock` (generated), `runner/src/lib.rs`, `runner/src/progress.rs`, `runner/src/main.rs`

**Interfaces:**
- Produces:
  - `pub struct JobError { pub category: &'static str, pub message: String }` in `lib.rs`; `category` is always one of the sheet's `ErrorCategory` words (sheet §3.3: `temporary`, `account`, `storage`, `integrity`, `unsupported`, `conflict`, `cancelled`, `internal`; an unknown word reads `internal`). `impl From<std::io::Error>` gives category `"storage"` and the error text as message.
  - The runner's failures map onto those words (decided here; the sheet fixes only the word list): I/O error `storage`; dump not usable (missing files, other title, SELF refusal) `integrity`; unsupported version or eboot hash `unsupported`; Noto fonts missing `unsupported`; relinker failed `internal`; real save folder in the run folder `conflict`.
  - `pub const STEPS: [&str; 5]` in `progress.rs`, exactly: `"Check the game dump"`, `"Unwrap the game files"`, `"Convert for Linux"`, `"Set up the game folder"`, `"Record the result"` (each 1 to 40 characters, sheet §3.2).
  - `pub struct Progress` with `pub fn from_env() -> Progress`, `pub fn to_writer(w: Box<dyn std::io::Write>) -> Progress`, `pub fn step(&mut self, index: usize, done: u64, total: u64, unit: &str, message: &str)`, `pub fn completed(&mut self)`, `pub fn error(&mut self, e: &JobError)`. `index` is the 0-based index into `STEPS` and is written as `step` unchanged (sheet §3.3: `step` is 0-based); build step N (1..=5, as numbered in this plan) sends `index` N-1. Each call writes one JSON line ending `\n` (at most 4096 bytes, sheet §3.3) and flushes; write errors are ignored (the host may have closed the pipe).
  - `main.rs`: `astroport-run build --dump <DIR> --data <DIR> [--install <DIR>]` and `astroport-run status --dump <DIR> --data <DIR> --version <V> [--install <DIR>]`; `--install` defaults to the parent of the folder holding the executable (`bin/..`). Usage errors print `usage: astroport-run build --dump <DIR> --data <DIR> [--install <DIR>] | status --dump <DIR> --data <DIR> --version <V> [--install <DIR>]` to stderr, exit 2. Build success exit 0; build failure writes the error line, prints the message to stderr, exit 1. Until Task 5 both subcommands return `JobError { category: "internal", message: "not built yet" }`. A run that ends without the final line (a panic, a kill) is read by the host as failed, `internal`, "The job stopped before it finished.", whatever the exit status (sheet §3.3), so `main` writes `completed` or `error` on every path it controls.

    use super::*;
    use std::sync::{Arc, Mutex};
    struct Buf(Arc<Mutex<Vec<u8>>>);
    impl std::io::Write for Buf {
        fn write(&mut self, b: &[u8]) -> std::io::Result<usize> { self.0.lock().unwrap().extend_from_slice(b); Ok(b.len()) }
        fn flush(&mut self) -> std::io::Result<()> { Ok(()) }

    fn lines(f: impl FnOnce(&mut Progress)) -> Vec<serde_json::Value> {
        let buf = Arc::new(Mutex::new(Vec::new()));
        let mut p = Progress::to_writer(Box::new(Buf(buf.clone())));
        f(&mut p);
        let text = String::from_utf8(buf.lock().unwrap().clone()).unwrap();
        text.lines().map(|l| serde_json::from_str(l).unwrap()).collect()
    }
    #[test]
    fn step_line_has_the_protocol_fields() {
        // index 1 = "Unwrap the game files" (build step 2); the wire `step` is 0-based (sheet §3.3)
        let v = lines(|p| p.step(1, 120, 400, "files", "libc.prx"));
        assert_eq!(v, vec![serde_json::json!({"step": 1, "done": 120, "total": 400, "unit": "files", "message": "libc.prx"})]);
    }

        let e = JobError { category: "unsupported", message: "Install the Noto fonts".into() };
        let v = lines(|p| { p.completed(); p.error(&e); });
        assert_eq!(v[0], serde_json::json!({"outcome": "completed"}));
        assert_eq!(v[1], serde_json::json!({"error": {"category": "unsupported", "message": "Install the Noto fonts"}}));
    }
    #[test]
    fn steps_are_the_five_design_steps() { assert_eq!(STEPS.len(), 5); assert_eq!(STEPS[2], "Convert for Linux"); }
}

**Interfaces:**
- Consumes: `JobError` (Task 1).
- Produces:
  - `pub fn unwrap(data: &[u8]) -> Result<Vec<u8>, String>`: the exact algorithm of `engines/anyps5/tools/unwrap_self.py` `unwrap()` (constants, `read_records`, `parse_elf`, `place_segments`, `check_decrypted`, region placement, header rewrite), returning the ELF bytes or the same refusal text the script prints after `FAIL: <input>: `.
  - `pub fn unwrap_file(src: &Path, dst: &Path) -> Result<u64, JobError>`: reads `src` (read-only), refuses `src == dst` (same file), a file starting with `\x7fELF` is copied unchanged, otherwise `unwrap`; writes `dst` through a temp file in the same folder then renames; returns the bytes written. A refusal is `JobError { category: "integrity", message: "<file name>: <refusal>" }`.
  - `tests/common/mod.rs` (shared by later tasks): `pub struct Seg { pub kind: u32, pub vaddr: u64, pub data: Vec<u8>, pub memsz: u64, pub align: u64, pub recorded: bool }`, `pub fn build_self(segs: &[Seg]) -> Vec<u8>`, `pub fn low_entropy(n: usize, seed: u8) -> Vec<u8>` (repeating 16-byte pattern), `pub fn high_entropy(n: usize, seed: u64) -> Vec<u8>` (xorshift64), `pub fn temp_dir(name: &str) -> PathBuf` (fresh `std::env::temp_dir()/astroport-run-test-<name>-<pid>-<counter>`, removed first if present).

`build_self` layout (what `unwrap_self.py` reads): u32 LE `0xEEF51454` at 0; one 0x20-byte record per `recorded` segment at `0x40 + i*0x20` = `(0x800 | phdr_index << 20, data_offset, len, len)` as four u64 LE, then an all-zero record; inner ELF header at `0x300` (`7f 45 4c 46 02 01 01 09`, `e_type` 0xFE10, `e_machine` 62, `e_version` 1, `e_phoff` 0x40, `e_ehsize` 64, `e_phentsize` 56, `e_phnum` = segs.len()); program headers at `0x340` with `p_offset` = the segment's offset counted from the inner ELF as if the segments were laid out back to back after the headers; segment data of recorded segments packed from `0x400` upward, each start rounded up to 0x10 only (not to `align`), so the packing breaks `p_align` the way real dumps do. Unrecorded segments with a vaddr point inside a PT_LOAD's file data.

## Interfaces with other steps

**Binary and CLI** (install folder `bin/astroport-run`, step 2 builds it with `cargo build --release --manifest-path runner/Cargo.toml`, output `runner/target/release/astroport-run`):

| Command | Output | Exit |
| --- | --- | --- |
| `astroport-run build --dump <APP_DIR> --data <DATA> [--install <INSTALL>]` | JSON progress lines (below) | 0 completed, 1 failed (error line written), 2 usage |
| `astroport-run status --dump <APP_DIR> --data <DATA> --version <V> [--install <INSTALL>]` | one line `{"state":"missing"\|"stale"\|"ready"}` on stdout | 0, 2 usage |

`<APP_DIR>` is the folder holding `eboot.bin` and `sce_sys/param.json` (step 3 finds it from `dump_folder`). `<INSTALL>` defaults to `<dir of the executable>/..`. `<V>` is a `version` value of `versions.json` (`1.018`, `1.019`).

**job.plan for `build`** (step 3 returns it; field names and rules from sheet §3.2 `JobPlan`, values decided here). The request is `job.plan {"job": "build", "game": "PPSA21567", "params": {}, "cleanup": false, "resume": null}` (sheet §3.2 `JobPlanParams`); the result:

```json
{"label": "Build game files",
 "steps": ["Check the game dump", "Unwrap the game files", "Convert for Linux", "Set up the game folder", "Record the result"],
 "argv": ["<install>/bin/astroport-run", "build", "--dump", "<APP_DIR>", "--install", "<install>", "--data", "<data>"],
 "env": {},
 "cwd": "<data>",
 "writable": ["<data>/generated", "<data>/saves"],
 "admission": {"blocks_launch": true, "pauses_while_playing": false, "runs_while_playing": false, "counts_against_downloads": false},
 "notify": {"completed": true, "failed": true},
 "changes_software": true, "resumable": false, "cleanup": false}
```

- `label` 1 to 80 characters, one line; `steps` 1 to 16 entries of 1 to 40 characters (= `runner/src/progress.rs` `STEPS`); `argv[0]` absolute and inside the install folder; `env` has no `AGS_` key (sheet §3.2 checks). `argv` is exactly step 3's `job_plan`; no `--version`, the runner detects it. `writable` folders are created 0700 by the host before the run (sheet §3.2 "as `LaunchPlan`", m1 §2.8).
- `changes_software: true` (it writes executables): the job always runs exclusive (no game starts while it runs, and it waits while a game runs, sheet §3.9), and it is refused from a paired device with `owner-only` (sheet §3.2). `blocks_launch: true`: a launch of the game while the job is unfinished is refused `job-blocks-launch` (sheet §3.9, §9).
- `cleanup: false`: after a cancel (SIGTERM to the group, SIGKILL after 10 s, sheet §3.4) the host never calls a cleanup plan; the next build removes `.stage/`. `resumable: false`: `jobs.pause` is refused `unsupported`, a host restart leaves the job `Failed` / `temporary` and `resume` stays `null` (sheet §3.4).
- The host runs the job with `PATH`, `HOME`, `LANG`, the plan's `env`, `AGS_JOB_PROGRESS_FD` and `AGS_JOB_ID` (sheet §3.3); the runner reads only `AGS_JOB_PROGRESS_FD`.

**Progress lines** (sheet §3.3; fd from `AGS_JOB_PROGRESS_FD`, else stdout): `{"step":I,"done":D,"total":T,"unit":U,"message":M}` with `I` the 0-based index into `steps`, 0..=4 (build step N sends N-1), then `{"outcome":"completed"}` or `{"error":{"category":C,"message":M}}`. `C` is an `ErrorCategory` word: `storage` (I/O), `integrity` (dump not usable), `unsupported` (version, eboot hash, missing Noto fonts), `internal` (relinker), `conflict` (save folder in the way). The host shows `steps[I]` as the job's `stage.word` and `status` (sheet §3.6, §3.7), and notifies "Build game files finished" / "Build game files failed" with the error message (sheet §3.10). `SHEET:` the one open line in `progress.rs` (where stdout goes).

**Generated executables** (sheet §3.5): after the job completes the host hashes every regular file with an execute bit under `<data>/generated/` (links not followed, at most 4096 files) into `<ext>/.generated.json`, and a launch whose `argv[0]` is `<data>/generated/run-<version>/AstroBot` is accepted only while that file's hash matches; otherwise it fails `generated-changed`. So: `run/AstroBot` must be a regular file with an execute bit (Task 5 step 4); a build run by hand outside a host job (development) leaves the recorded hash stale until the job runs once; an install, repair or rollback of AstroPort removes `.generated.json`, so after every update the build job must run before the game launches.

**Presets:** the design (5.2) says the runner does "the preset loading itself". Presets are env for the launch, and the launch env is built by step 3's `launch.plan` from `<install>/presets/*.json` (play-hybrid.sh's Python one-liner: every key not starting with `_` with a string value becomes a variable). The runner does not load or copy presets; step 3 owns that.

**Install folder:** no change to the fixed layout. The runner reads `anyps5/relinker`, `anyps5/libs/*.prx`, `anyps5/libAstroHybridHost.prx`, `shims/*.prx`, `lib/libkyty_gpu.so`, `lib/libnvidia-ngx-dlss.so.*` (optional), `patches/versions.json`, `ags-extension.toml` (the `version` line). Step 2: keep the three forwarders in `shims/` only (the runner lays them over AnyPS5's own `libSceAgc*.prx`/`libSceVideoOut.prx` from `anyps5/libs/`).

**Rebuild after an update:** the adapter's rule is the record's `release` against the installed version (step 3 `dump::built()`), so every AstroPort update offers the job (never runs it on its own); the host's removal of `.generated.json` on that update (sheet §3.5) makes the launch fail `generated-changed` until the job has run, which agrees with that rule. The adapter does not call `status`; `inputs_sha256` and `status` stay runner-internal (development and tests).
